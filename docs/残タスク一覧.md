## 📊 実運用OOS監視（恒久ルール・2026-04-07策定）

**2020-2025は全部「見てしまったデータ」。唯一の真のOOSは2026年以降の実運用成績。**

### 崩壊検知モニター（2026-04-20 実装）

```bash
python scripts/analysis/rolling_roi_monitor.py --start 2020-01-01 --end $(date +%Y-%m-%d)
```

**STOP/WARNING が出たときの正しい解釈**:

出力に `[統計 XXX] 正常でもYY%で発生 (誤検知の可能性: 高/中/低)` が表示される。
- **誤検知の可能性: 高（YY% ≥ 30%）** → 何もしない。年次退出基準で判断。
- **誤検知の可能性: 中（10% ≤ YY% < 30%）** → 月次モニタリング強化。停止は保留。
- **誤検知の可能性: 低（YY% < 10%）** → 本物の崩壊シグナルとして調査開始。

**設計上の限界（Opus指摘 2026-04-20）**:
- 三連単1点買い（的中率0.7-2%）では100件ウィンドウは小さすぎる
- D_P143（0.7%）の5%有意ラインは **約426件**（≈1.5年分）
- C_P132（1.8%）の5%有意ラインは **約157件**（≈1.3年分）
- 現行ルールは「参考シグナル」として使用し、最終判断は年次退出基準で行う

## 🔰 ロジック変更の検証ルール（恒久ルール）

**予測再生成の前に必ず影響範囲をDBで確認する（Phase 0）。**

### 手順

1. **Phase 0（数秒〜1分）**: 変更が実際に何レースに影響するかをSQLで確認
2. **判断**:

| 影響率 | 判断 |
|--------|------|
| < 1% | 予測変化はほぼゼロ。全再生成不要と判断できる |
| 1〜5% | 影響中程度。1年分の部分再生成で傾向把握してから判断 |
| > 5% | 影響大。**全年度再生成 + フルバックテスト必須**（偶然を排除するには全数調査しかない） |

3. **全再生成が必要な場合**: 部分サンプル・特定期間では偶然を排除できないため、必ず全6年分を再生成してフルバックテスト（`--full`）で比較する

### 変更種別ごとのPhase 0確認クエリ例

```sql
-- 天候・気象条件が関係する変更
SELECT weather, COUNT(*) FROM race_conditions GROUP BY weather ORDER BY COUNT(*) DESC;

-- 会場フィルター変更
SELECT venue_code, COUNT(*) FROM races GROUP BY venue_code ORDER BY venue_code;

-- オッズ範囲変更（対象レースの件数確認）
SELECT COUNT(*) FROM trifecta_odds WHERE odds BETWEEN :新min AND :新max;
```

※ actual_course vs pit_number の確認クエリは「⏸️ actual_course修正の検証」タスクを参照

### ⚠️ 注意
- 再生成中に別のロジック変更を入れると予測が混在する → **再生成完了まで新規変更禁止**
- 「1日分のCSV比較」や「1年分の部分再生成」は期間選択の偶然性を排除できない

### ⏸️ P1: pairwise_scoring改善【2026-03-23 中断・不採用記録済み】

**経緯（2026-03-19〜2026-03-23）**:
- 案C（1着固定・2-3着をget_second/third_place_probs()で変更）を実装・全年度before再生成して検証
- **結果**: OFF: 3,239件/174.1%/+239,890円 → ON: 2,018件/127.3%/+55,178円（**大幅悪化**）
- DB復元（`data/boatrace_backup_pairwise_test.db`）でpairwise=OFF状態に戻し中断
- `docs/improvement_attempts/REJECTED_IDEAS.md` に不採用理由を記録済み

**悪化の主因（Opusで分析）**:
1. **件数-38%**: 2-3着順位変更→買い目変更→オッズフィルター(30-70倍)通過率低下
2. **ROI悪化**: `get_second/third_place_probs()` が確率の積で計算（独立性仮定違反・誤差増幅）
3. **2020年特悪**: pairwiseモデルが2021-2024学習→2020年は学習データ外かつrace_predictions充足率51%
4. **循環依存**: モデルがtotal_scoreを特徴量→予測ロジック変更のたびに再学習必要

**将来の再試行を検討する場合の改善案**:
- `get_second/third_place_probs()` をwin_count方式（ΣP(i>j)の和）に変更（各~5行）
  - 参考: `src/ml/pairwise_rank_model.py` L449-496（`reconstruct_rankings(method='win_count')`既存実装）
- pairwiseモデルからtotal_score特徴量を除外して再学習（循環依存の解消）
- **条件**: 改善後でも全年度バックテストでpairwise=OFF基準（+239,890円）を上回ることを確認

### ⏸️ P5: Stage 2 信頼度A基準緩和（gap 15 → 12）【条件付き保留】

**背景**: Stage 2のA基準（gap>=15）が厳しすぎ。全レースの80%以上でtotal_score>=80なのにC判定に落とされるケースが多い。
**修正**: `race_predictor.py` L1680: `score_gap >= 15` → `score_gap >= 12`

**2026-03-13 検証結果**: 現C信頼度のみ3条件体制では有害
- gap=12: 件数1,326→306（-77%）、ROI 124.0%→97.5%、収支+31,877→-761円、黒字年5→3年
- 原因: gap 12-14の1,020件がC→A昇格 → C条件から外れ件数激減
- **実施条件変更**: gap緩和は全条件でA判定増加をもたらす（C条件3つも含む）→ Tier2で全条件への影響を検証してから判断（Opus 2026-03-16評価: 「A条件追加が前提」という保留理由は論理的飛躍。正確には「全条件へのTier2検証が必要」）
