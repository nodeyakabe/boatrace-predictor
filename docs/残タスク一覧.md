## 🔰 ロジック変更の検証ルール（恒久ルール）

**予測再生成の前に必ず影響範囲をDBで確認する（Phase 0）。**

### 手順

1. **Phase 0（数秒〜1分）**: 変更が実際に何レースに影響するかをSQLで確認
2. **判断**:

| 影響率 | 判断 |
|--------|------|
| < 1% | 予測変化はほぼゼロ。全再生成不要と判断できる |
| 1〜5% | 影響中程度。1年分の部分再生成で傾向把握してから判断 |
| > 5% | 影響大。**全年度再生成 + フルバックテスト必須**（偶然を排除するには全数調査しかない） |

3. **全再生成が必要な場合**: 部分サンプル・特定期間では偶然を排除できないため、必ず全6年分を再生成してフルバックテスト（`--full`）で比較する

### 変更種別ごとのPhase 0確認クエリ例

```sql
-- 天候・気象条件が関係する変更
SELECT weather, COUNT(*) FROM race_conditions GROUP BY weather ORDER BY COUNT(*) DESC;

-- 会場フィルター変更
SELECT venue_code, COUNT(*) FROM races GROUP BY venue_code ORDER BY venue_code;

-- オッズ範囲変更（対象レースの件数確認）
SELECT COUNT(*) FROM trifecta_odds WHERE odds BETWEEN :新min AND :新max;
```

※ actual_course vs pit_number の確認クエリは「⏸️ actual_course修正の検証」タスクを参照

### ⚠️ 注意
- 再生成中に別のロジック変更を入れると予測が混在する → **再生成完了まで新規変更禁止**
- 「1日分のCSV比較」や「1年分の部分再生成」は期間選択の偶然性を排除できない
