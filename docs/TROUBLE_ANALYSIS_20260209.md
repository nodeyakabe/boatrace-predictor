# トラブル分析レポート: 日付形式混在問題

**発生日**: 2026-02-09
**影響範囲**: DB全体（307,233件のレースデータ）
**解決所要時間**: 約1時間

---

## 📋 トラブル概要

### 発見された問題

1. **日付形式の混在**
   - YYYYMMDD形式: 37,320件（2021年1-8月）
   - YYYY-MM-DD形式: 307,233件（全期間）

2. **データの二重投入**
   - 2021年1-8月のデータが2つの形式で重複
   - 重複レース: 37,320件
   - 重複オッズ: 3,623,073件

3. **重複プロセスの同時実行**
   - `自動実行_2日間_完全収集_再開可能版.py`
   - `補完_2021_2023_完全版.py --year 2021 --month 9`
   - 同じ期間を同時に収集・投入していた

---

## 🔍 根本原因分析

### 原因1: 投入スクリプトの不完全な修正

**問題箇所**: `scripts/maintenance/投入_2021_2023_補完データ.py`

| 関数 | 日付変換コード | 状態 |
|------|--------------|------|
| `import_races` | ❌ **なし** | **問題の根本原因** |
| `import_entries` | ❌ なし | - |
| `import_results` | ❌ なし | - |
| `import_payouts` | ❌ なし | - |
| `import_trifecta_odds` | ✅ **あり** | 正常 |
| `import_race_conditions` | ❌ なし | - |
| `import_race_details` | ✅ **あり** | 正常 |

**タイムライン**:

1. **2026-02-06頃**: 日付形式バグを発見
   - `import_trifecta_odds`と`import_race_details`を修正
   - **しかし`import_races`は修正し忘れ**

2. **2026-02-06 17:16**: 2021年1-8月のDB投入
   - CSVはYYYY-MM-DD形式
   - `import_races`に変換コードがないため、そのまま投入
   - 結果: YYYY-MM-DD形式で投入された

3. **それ以前**: 2021年1-8月のデータが既にYYYYMMDD形式で存在
   - 古い収集・投入で作成されたデータ

4. **結果**: 同じレースが2つの形式で存在

**修正すべきだったコード**:


### 原因2: CSVファイルの日付形式の不統一

**問題**:
- 古いCSV（収集時期不明）: YYYYMMDD形式
- 新しいCSV（2026-02-06以降）: YYYY-MM-DD形式

**なぜ形式が変わったか**:
- `補完_2021_2023_完全版.py`が出力する形式がYYYY-MM-DD
- しかしDB投入時にYYYYMMDDに変換する前提だった
- その変換コードが一部の関数にしかなかった

---

### 原因3: 重複プロセスの制御不足

**問題**:
- `自動実行_2日間_完全収集_再開可能版.py`が実行中
- 手動で`補完_2021_2023_完全版.py`を実行
- 進捗管理ファイル（`.collection_progress.json`）が共有されていない

**結果**:
- 同じデータを異なるプロセスが収集
- リソースの無駄遣い
- データの整合性リスク

### 優先度4: 日付形式の統一ポリシー確立（推奨）

**決定すべきこと**:
1. **DB内部の日付形式をどちらに統一するか**
   - Option A: YYYYMMDD形式（現状維持）
   - Option B: YYYY-MM-DD形式（SQL標準）

2. **CSV出力の日付形式を統一**
   - 収集スクリプトが出力する形式を統一
   - 投入スクリプトがどちらでも受け入れられるようにする

**推奨**: **YYYY-MM-DD形式に統一**

**理由**:
- SQLのBETWEEN句が直感的に使える
- ISO 8601標準に準拠
- 多くのツールで認識しやすい

**実施方法**:
1. `scripts/data_collection/補完_2021_2023_完全版.py`
   - 既にYYYY-MM-DD形式で出力（修正不要）

2. `scripts/maintenance/投入_2021_2023_補完データ.py`
   - YYYY-MM-DD形式をそのまま受け入れる
   - YYYYMMDDへの変換を削除

3. 既存のYYYYMMDD形式データをYYYY-MM-DD形式に変換
   - **今回実施済み** ✅

**所要時間**: ドキュメント化のみ（30分）
**効果**: 将来の混乱を防止

## 💡 教訓

### 技術的教訓

1. **部分修正は危険**
   - 一部の関数だけ修正すると、見落としが発生
   - 関連する全ての関数を一括修正すべき

2. **日付形式の統一は最優先**
   - 日付は全システムで最も基本的なデータ型
   - 統一ポリシーを早期に確立すべき

3. **プロセス間の調整は必須**
   - 複数のデータ収集スクリプトが存在する場合
   - ロック機構や進捗共有が必要

### プロセス的教訓

1. **修正の完全性チェック**
   - コード修正後、関連する全箇所を検索
   - 同じパターンが他にないか確認

2. **テスト環境の重要性**
   - 本番DBに直接投入する前にテスト
   - `--dry-run`オプションの活用

3. **ドキュメントの維持**
   - 設計方針を明文化
