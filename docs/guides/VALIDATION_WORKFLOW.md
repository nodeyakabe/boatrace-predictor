## 概要

### 3段階検証の目的

| Tier | 目的 | 期間 | 合格基準 | 所要時間 |
|------|------|------|----------|----------|
| **Tier 1** | 簡易スクリーニング | 2年間（2024-2025） | ROI 150%+, 1/2年黒字, 50件+ | ~10秒 |
| **Tier 2** | 本格検証 | 6年間（2020-2025） | ROI 100%+, 4/6年黒字 | ~30秒 |
| **Tier 3** | 実装一致確認 | 6年間（2020-2025） | Tier 2との一致率 95%+ | ~60秒 |

### なぜ3段階が必要か？

1. **Tier 1: 無駄な作業を避ける**
   - 明らかに性能が低い条件を早期に除外
   - Tier 2（6年間）の重い処理を回避

2. **Tier 2: 長期安定性を確認**
   - 6年間のデータで本格的な性能評価
   - 年度別の黒字/赤字パターンを確認

3. **Tier 3: 実装乖離を防止**
   - バックテストと実運用コードで同じ結果が出るか検証
   - 見落としがちな実装ミスを検出

- **1/2年黒字**（2024年または2025年が黒字）

## Tier 2: 標準テスト（6年間）

### 目的

6年間（2020-2025）の長期データで本格的な性能評価を行います。Tier 1を通過した条件のみを対象とします。

### 合格基準

- **ROI 100%以上**（6年間累計）
- **黒字年数 4/6年以上**
- **累計収支がプラス**
- **unique割当件数 50件以上**（重複除外後の実運用シミュレーション）⭐2026-05-20追加
- **unique的中数 10件以上**（6年間累計）⭐2026-05-20追加

> **⚠️ 採用判断はunique数値のみで行う**: non-unique（条件別最大ポテンシャル）は探索段階の参考値に限定。
> unique件数が少ない条件は、優先度の高い他条件に先取りされており、実運用では機能しない。
> **教訓（v2.64.0・2026-05-20）**: C_P132_100_200_NARUTO は non-unique 592件/ROI 142%で採用されたが、
> unique 実態は 50件/1的中（5/6年赤字）。priority dedup により実質的に機能していなかった。

### Tier 3で不合格の場合

```
[Tier 2との比較]
----------------------------------------------------------
  Tier 2購入件数: 3,200件
  Tier 3購入件数: 2,850件
  一致率:         89.06%

----------------------------------------------------------
  一致率:   89.06% (基準:   95.00%以上) ❌ FAIL

  総合判定: ❌ 不合格（実装に乖離があります）

  【推奨アクション】
    1. Tier 2とTier 3のロジック差異を調査
    2. config/bet_conditions.py の条件定義を確認
    3. BetTargetEvaluator の実装を確認
    4. オッズデータ、予測データの取得方法を確認
```

#### よくある原因

1. **条件定義の不一致**
   - `config/bet_conditions.py` に条件が追加されていない
   - 条件のパラメータが異なる（オッズ範囲、会場フィルター等）

2. **オッズ取得の違い**
   - Tier 2は `trifecta_odds` テーブルから直接取得
   - Tier 3は実運用ロジック（`get_odds_data()`）を使用
   - パターンH対応が漏れている（1-2-3, 1-2-4, 1-2-5）

3. **予測データの違い**
   - `prediction_type = 'before'` の確認
   - `rank_prediction` の順序確認

4. **会場コードの型違い**
   - Tier 2: 整数（1, 2, 3, ...）
   - Tier 3: 文字列（'01', '02', '03', ...）

5. **⚠️ 新規フィルターキーが `BetTargetEvaluator` に未実装（2026-05-20 追加）**
   - `config/bet_conditions.py` に**既存条件で使われていない新しいキー**を使った条件を追加した場合
   - `backtest_helpers.py` にはSQLフィルターを実装したが、`src/betting/bet_target_evaluator.py` の `evaluate()` への実装を忘れると、バックテストでは正しくフィルターされるが**実運用では完全スルー**になる
   - 実際の事例: `D_ST_CONTRAST_100_300` の `pit1_st_min`/`pit2_st_max` （2026-05-20 発覚・修正）
   - **確認方法**: 条件で使う全キーが `evaluate()` の `optional_fields` に登録され、フィルターロジックも実装されているか確認する

   **現在 `backtest_helpers.py` にはあるが `BetTargetEvaluator` に未実装のキー（将来使用時は要実装）**:

   | キー | backtest SQL | 用途 |
   |-----|-------------|------|
   | `predicted_rank_has_class` / `predicted_rank_range` | 予測順位範囲内に指定級別がいるか | 特殊条件用 |
   | `min_score_gap` | 1位-2位スコア差フィルター | 差の大きいレース絞り込み |
   | `min_score_gap_3_4` | 3位-4位スコア差フィルター | 同上（下位差） |
   | `p1_motor_second_rate_min` | 1着予測選手のモーター2連率下限 | モーター条件 |
   | `p1_avg_st_max` | 1着予測選手のST安定度上限 | ST条件 |
   | `p1_not_course1` | 1着予測が1号艇でない | 穴条件 |

## トラブルシューティング

### Q1: Tier 1で異常に高いROI（300%超）が出る

**原因**: サンプル数が少ない、または特定の高額的中に偏っている

**対応**:
- サンプル数を確認（50件未満なら不合格）
- Tier 2で6年間の長期検証を実施

---

### Q2: Tier 2とTier 3で大きな乖離（一致率80%以下）

**原因**: 実装ロジックの違い

**チェックリスト**:

1. **条件がconfig/bet_conditions.pyに追加されているか？**
   ```python
   from config.bet_conditions import get_condition_by_id
   cond = get_condition_by_id('NEW_CONDITION')
   print(cond)  # Noneなら追加漏れ
   ```

2. **会場コードの型が一致しているか？**
   - Tier 2: `venue_filter: [1, 2, 3]` （整数）
   - Tier 3: `venue_code = '01', '02', '03'` （文字列）
   - 変換処理: `venue_code = int(venue_code_str)`

3. **オッズ取得ロジックが一致しているか？**
   - パターンH: 1-2-3, 1-2-4, 1-2-5の3点
   - 1点買い: 1-2-3のみ

4. **予測データの取得条件が一致しているか？**
   - `prediction_type = 'before'` を使用
   - `rank_prediction = 1, 2, 3` の順序

---

### Q3: Tier 2で6年間ROI 150%だが、2025年だけ赤字

**原因**: 過学習、または市場環境の変化

**対応**:
- 年度別の内訳を確認
- 直近2年（2024-2025）が連続赤字なら不採用を検討
- 2025年のみ赤字で、2024年は黒字なら継続観察

---

### Q4: Tier 1合格、Tier 2不合格（ROI 95%）

**原因**: 直近2年に偏った性能、長期では不安定

**対応**:
- Tier 2の基準（ROI 100%+, 4/6年黒字）を満たさない条件は不採用
- 不採用案として `docs/improvement_attempts/REJECTED_IDEAS.md` に記録

---

### Q5: 条件を削除したい

**手順**:
1. `config/bet_conditions.py` から条件を削除
2. 標準テストを再実行して全体ROIを確認

```bash
python scripts/backtest/standard_backtest.py --full
```

3. 削除理由を `docs/improvement_attempts/REJECTED_IDEAS.md` に記録

---

## まとめ

### 検証フローのチェックリスト

- [ ] Tier 1: 簡易テスト（2年間）実行
  - [ ] ROI 150%以上
  - [ ] 1/2年黒字
  - [ ] サンプル数 50件以上
- [ ] Tier 2: 標準テスト（6年間）実行
  - [ ] 条件を `config/bet_conditions.py` に追加
  - [ ] `standard_backtest_unique.py --full` 実行（unique版で最終判定）
  - [ ] ROI 100%以上（unique版）
  - [ ] 4/6年黒字（unique版）
  - [ ] 累計収支プラス（unique版）
  - [ ] **unique件数 50件以上**（⭐必須）
  - [ ] **unique的中数 10件以上**（⭐必須）
  - [ ] **二項検定: IS期間の的中率がランダム(1/120)と有意差あるか確認**（⭐2026-05-25追加）
    - unique的中数が20件未満の場合は必須。p ≥ 0.05なら採用禁止
    - 計算例: `scipy.stats.binomtest(hits, n_bets, 1/120, alternative='greater').pvalue`（scipy 1.7+）
  - [ ] **E信頼度条件の場合は採用禁止**（confidence='E' は confidence_filter.py デフォルト除外対象）
  - [ ] **market_diverge条件の場合は月次件数確認**（月2件未満なら6年通算でも少数すぎ）
- [ ] **新規フィルターキー確認**（条件追加時のみ・Tier 2前に実施）
  - [ ] 条件で使う全キーが過去に他の条件でも使われているか確認
  - [ ] **新規キーの場合**: `backtest_helpers.py` の SQL フィルターと `BetTargetEvaluator.evaluate()` の両方に実装する
  - [ ] 新規キーを `evaluate()` の `optional_fields` リストに追加する
- [ ] Tier 3: 実環境確認
  - [ ] `verify_prediction_consistency.py` 実行
  - [ ] Tier 2との一致率 95%以上
- [ ] 最終更新
  - [ ] Tier 2結果を `config/bet_conditions.py` に反映
  - [ ] 変更をコミット

### 重要なポイント

1. **Tier 1不合格の条件をTier 2に進めない**
   - 時間の無駄、リソースの無駄

2. **Tier 2不合格の条件を本番適用しない**
   - 長期で赤字になる可能性が高い

3. **Tier 3不合格の条件は実装を修正**
   - バックテストと実運用の乖離は致命的なバグ

4. **不採用案も記録する**
   - 同じ過ちを繰り返さない
   - `docs/improvement_attempts/REJECTED_IDEAS.md` に追記

5. **採用判断はunique数値のみで行う**（⭐2026-05-20追加）
   - non-unique（重複あり版）は探索段階の参考値。最終採用判定に使ってはならない
   - `standard_backtest_unique.py --full` の結果で unique 件数・的中数・ROIを確認すること
   - **unique 50件未満、または unique 的中数 10件未満は原則不採用**
   - C_P132_100_200_NARUTOの教訓: non-unique592件で採用→unique実態50件/1的中で機能不全

6. **新規フィルターキーは backtest と実運用の両方に実装する**（⭐2026-05-20追加）
   - `config/bet_conditions.py` に新しいキー（既存条件未使用）を使った条件を追加したら、必ず `backtest_helpers.py` と `BetTargetEvaluator.evaluate()` の**両方**にフィルターを実装する
   - どちらか片方だけでは「バックテストでは機能するが実運用ではスルー」または「実運用では機能するがバックテストに反映されない」という乖離が生じる
   - 実装後は Tier 3 で一致率 95%+ を確認する

7. **edge（優位性）は統計的に検証する**（⭐2026-05-20追加）
   - 的中数が少ない（3的中以下）条件は二項検定でランダムと区別できるか確認する
   - D_P132_100_200_HIROSHIMAの教訓: 6年3的中(p=0.32)はランダムと区別不能 → 廃止

8. **稼働中条件への採用基準の遡及適用は禁止**（⭐2026-05-20追加）
   - Tier 2合格基準（unique 50件以上・10的中以上・4/6年黒字）は**新規採用時のみ**適用する
   - 稼働中条件を「6年通算50件未満」「的中数が採用基準以下」等の理由で廃止候補としてはならない
   - 稼働中条件の廃止判断は**退出ルール（ROI基準）のみ**に基づく
   - 教訓: C_B1_30_50_ASHIYA/C_TSU_B1_30_50 — 採用基準を遡及適用して廃止候補としたが、直近3年ROIは186-343%で退出ルール上は全く問題なし（2026-05-20 Opus二重検証）

9. **事後パターン認識による廃止判断は禁止**（⭐2026-05-20追加）
   - 「2022年と2025年のみ的中」等の事後発見年別パターンは廃止根拠にならない
   - 2020-2025は「見てしまったデータ」。パターン探索すれば何らかの規則性が必ず見つかる（データスヌーピングの典型的な罠）
   - 廃止根拠として有効なのは: ①退出ルール（ROI基準）、②二項検定（p値でランダムと区別不能）、③件数減衰（年4件未満×2年連続）のみ

10. **低N条件・market_diverge条件には追加ガードレールを適用**（⭐2026-05-25追加）
    - **二項検定でIS期間のedgeを検証する**（三連単ランダム的中率 = 1/120 = 0.833%）
      - p ≥ 0.05: 統計的根拠なし → 採用禁止
      - 0.05 > p ≥ 0.10: 弱い証拠 → OOS 50件以上蓄積後に再判定
      - p < 0.05: 採用可（それでも OOS 検証を推奨）
    - **unique的中数が20件未満の場合はOOS検証必須**: Tier2通過後も2026年OOSで50件以上・2的中以上を確認してから正式採用
    - **E信頼度（confidence='E'）条件の禁止**: `confidence_filter.py` の `exclude_e_level=True`（デフォルト）との設計矛盾。E信頼度条件を採用する場合は `exclude_e_level` のデフォルト動作を変更しなければならず、既存全条件への影響が生じる
    - **market_diverge系条件の注意点**: use_market_diverge=Trueは独立信号に見えるが、件数が少ない（月2件未満）と6年間でも20件以下になり統計的判断が不可能。IS ROIが高くても二項検定が優先
    - **教訓（2026-05-25 Opus確認）**: E_DIVERGE_100_200はIS 842件/7的中（p=0.553・完全ランダム）。Tier2形式的PASS（5/6年黒字・ROI 195%）したがIS=ランダムと確定 → 廃止。A_DIVERGE_80_100はIS p=0.255（未達） → 凍結監視中

11. **凍結監視（active=False）の使い方**（⭐2026-05-25追加）
    - Tier2形式通過したが統計的根拠が不十分な条件は「廃止」ではなく「凍結監視」とする
    - `config/bet_conditions.py` に `'active': False` を追加し、`frozen_date` と `freeze_reason` を記録
    - **`active=False` を適用するファイル（修正必須）**: 凍結条件を追加・解除するたびに以下が全て `get_active_conditions()` を使っているか確認すること
      - `scripts/backtest/standard_backtest_unique.py` — バックテスト（unique）
      - `scripts/backtest/standard_backtest.py` — バックテスト（non-unique）
      - `scripts/backtest/fast_backtest.py` — 高速バックテスト
      - `src/betting/bet_target_evaluator.py` — **実運用購入判定**（最重要）
      - `scripts/automation/reconcile_yesterday_bets.py` — 昨日購入再現
      - `scripts/validation/verify_prediction_consistency.py` — Tier3一致率検証
    - 凍結解除基準の例: 「OOS 50件以上蓄積・ROI 150%以上・的中数≥5件」（月5件ペースで10ヶ月）
    - 凍結監視中の条件は毎月の標準テストで個別確認する方法:
      ```bash

      python scripts/backtest/quick_condition_test.py --condition-id "A_DIVERGE_80_100"
      ```

## ⚠️ 統計的落とし穴への継続対策（2026-04-07追加・Opus検証済み）

### 根本的な問題の認識

2020-2025の6年間データで条件を発見・選定してきたため、このデータは「見てしまったデータ」であり真のOOSとして使えない。**唯一の真のOOSは2026年以降の実運用成績**。

---

### 新条件探索の制約

**2020-2025データでの新条件探索は原則停止**

- 探索空間（会場×ランク×オッズ帯）はREJECTED_IDEAS.mdに記録された通り網羅的にスキャン済み
- 同じデータで繰り返し探索すると偽発見率（FDR）が累積的に上昇する
- **例外**: 予測ロジック自体を変更した場合（新モデル導入等）は再探索可

**次のROI改善の優先順位**:
1. 予測モデル自体の精度向上（全条件に横断的に効く）
2. 買い目生成ロジックの改善（パターンH適用拡大等）
3. 2026年以降データが蓄積されてからの新条件探索

---

### 既存条件の定期監視・退出ルール

#### 記録頻度

| 頻度 | 対象 | 内容 |
|------|------|------|
| **月次** | 全体ポートフォリオ | ROI・収支・件数を記録（判断は不要、記録のみ） |
| **半年** | 全体ポートフォリオ | ROI < 100% なら原因調査開始 |
| **年次** | 条件別 | 年間成績で退出判定を実施 |

> ⚠️ **四半期の個別条件ROIは判断材料にならない**: 年200件の条件では四半期約50件。95%信頼区間が0〜200%に広がり統計的に無意味。判断最小単位は**半年・全体ポートフォリオ**。

#### 退出判定基準

| 年間件数 | 廃止検討の基準 |
|:-------:|--------------|
| **100件以上** | 直近2年連続でROI < 100% |
| **100件未満** | 直近3年累計でROI < 100% |
| **年5件未満（超低件数）** | 年4件未満が2年連続（構造的件数減衰の可能性） |

> ⚠️ **退出ルールは廃止の必要条件**: 上記ルールを満たさない限り廃止しない。「件数が少ない」「ROIが低そうに見える」「的中が少ない」等は補助情報であり単独では廃止根拠にならない。

**採用後最低運用期間（ロックアウト）**:
- 採用後**12ヶ月または累計50件追加**が経過するまで廃止検討対象外
- 採用直後の変動は統計的ノイズの範囲内であり、退出ルールを適用するのに十分なデータがない

**廃止判断時の必須確認**:
- 退出ルール（上記ROI基準 or 年4件未満×2年連続）を満たしているか？ → 満たしていなければ廃止しない
- 採用後12ヶ月または累計50件追加が経過しているか？ → 経過していなければ廃止検討対象外
- 「配当分布の変化」vs「的中率の低下」を切り分けること
- **配当分布変化なし＋的中率低下** → 予測精度の問題 → 廃止妥当（びわこの教訓）
- **配当分布も変化** → 市場の構造変化 → 条件変更で対応できる可能性あり

#### 要注意条件（2026-04-07時点）

以下2条件はびわこと同じ「Tier2基準ギリギリ・絶対収益が小さい」構造。優先的に監視すること。

| 条件 | 年間件数 | 6年収支 | リスク |
|------|:-------:|:-------:|------|
| 丸亀+尼崎+蒲郡×A×B1×30-50 | ~17件 | +1,060円 | 1的中で見え方が大きく変わる水準 |
| 津+浜名湖+若松×A×A2×30-50 | ~6件 | +1,170円 | 同上・年6件は統計的判断不能 |
